# Week of Us security and reliability audit — 2026-10-03

This audit found material calendar confidentiality gaps, a transferable Google account-linking flow, and native offline drafts that lacked household identity. Fixes are confined to the local `audit/week-of-us-hardening-20261003` branch. The original `/Users/jgreco/code/planner` checkout remains on `main` at `ae224b5`; its five preexisting planner filter/UI changes were inspected read-only and preserved. No production data, calendars, invitations, grants, security settings, pushes, or deployments were changed.

The requested GPT-6 Astra xhigh auditor reviewed the security boundaries and collaborated on the calendar/auth/native fixes. Repository `AGENTS.md`, installed Next.js security documentation, and the security-best-practices skill informed the audit. This report distinguishes source evidence and synthetic regressions from actual production exploitation, which was neither attempted nor established.

## Deployment gate: preserve historical data

**Use the final audit branch, never the earlier `8706a2b` migration by itself.** The original audit implementation used deletion cascades; it was revised before release. Final migration 020 performs non-destructive authorization quarantine: it retains calendar preferences, collaboration entries, attachment bytes, ownership, hidden-event records, reminders, notification bodies and delivery history. It hides departed calendars, expires derived caches, and marks future notification work revoked. No physical cleanup migration is included or authorized.

**Rollback floor:** after migration 020, `88c34e7` is the minimum compatible remediation revision: every web/native-API server and notification worker must retain the final quarantine authorization/claim filters and the household-scoped calendar conflict target. Earlier binaries are incompatible: old workers ignore revocation timestamps and can rematerialize retained reminders; the old calendar upsert also expects a replaced uniqueness constraint. A regression demonstrates that the legacy due-reminder query selects a quarantined row while the compatible query excludes it. Do not blindly roll back to pre-audit code or reverse quarantine markers. If cutover fails, stop affected workers/routes, retain the data and migrations, then deploy a compatible corrected build. Restoring service with an earlier vulnerable binary is not an approved recovery plan.

Review the schema and quarantine counts in a staging copy and take a tested backup before any production migration. A later physical cleanup would require its own affected-row dry run, recoverable backup/restore procedure and explicit approval. No production rows were inspected or changed in this audit. This is a local, tested remediation branch; deployment remains outside scope.

## Material findings

### WOU-01 — High: private event titles broadcast to household members — fixed locally

Original evidence: `src/app/actions/calendar.ts:90–98,166–171,224–229` allowed an owner to edit a Private calendar and then passed its draft title to `queueHouseholdChange`. `src/lib/server/notifications.ts:287–305` queued that body for other household members who enabled change alerts; the inbox/email/push paths consume the stored body without source-calendar authorization.

Prerequisite and impact: an ordinary create/update of a private event through Week of Us, plus another household member with change alerts enabled, would disclose the event title. No attacker-crafted request was necessary. Private deletion would disclose that a change occurred, but not its title.

The fix checks source/destination visibility before household notification creation, including moves. Regression tests cover private create/update/delete and Private/Share moves while retaining shared notifications. Previously delivered messages cannot be recalled. Historical outbox rows lack source-calendar identifiers, so selective historical cleanup cannot be safely inferred; no real data cleanup was attempted.

### WOU-02 — High: departed members' provider calendars remained reachable — fixed locally

Original evidence: `src/app/actions/settings.ts` removal/leave deleted membership while `calendar_preferences` referenced users and households separately. `src/lib/server/calendar-data.ts:267–300` searched remaining preferences using the departed owner's Google token without checking current owner membership. Reminders and local event attachments also relied on the stale preference.

Prerequisite and impact: a former member previously shared a calendar, retained a valid Google connection, and another member remained in the old household. Ordinary old-household searches could retrieve subsequent provider events within the app's previous-year/next-two-years search interval. Relevant event data can include title, description, location, dates/times and attendees as mapped by the provider adapter. This was continuing provider access, beyond already cached copies.

The fix checks owner membership across search, refresh, calendar mutation, metadata, reminder, attachment/collaboration and coverage paths. Commit `88c34e7` revises final migration `020_membership_privacy.sql` and its matching worker authorization. The migration preserves existing records and file bytes, hides orphan/departing preferences, expires caches, quarantines reminders/outbox work and skips unsent channels. Delivered status is retained. Membership-locking triggers reject stale new writes and preserve revocation during races. Preferences are unique per household/user/provider calendar so discovering the same calendar in a new household cannot move old attachments or prevent reconnecting. Rejoining keeps old calendars hidden and historical notifications revoked until a new authorized choice is made.

Database tests prove retention of content/ownership/files, revocation of recipient and calendar-owner reminders, preservation of delivered history, rejection of stale enqueues, and fresh hidden defaults. A separate upgrade regression creates pre-020 orphan history, applies the migration, and verifies retained bytes and revoked work. Explicitly restoring a revoked reminder assigns a fresh delivery version, allowing the same schedule to be chosen again without reviving its old outbox history; untouched reminders preserve existing deduplication. Provider grants/accounts remain intact.

Release prerequisite: deploy the final non-destructive migration and its matching application filters together, with the old job worker stopped during cutover. The superseded cascading migration must not be deployed. An already-in-flight provider request or external notification cannot be atomically recalled. Previously authorized copies already delivered to other members and historical digest/change messages without source identifiers cannot be selectively attributed or erased safely; no blanket cleanup is included.

### WOU-03 — High: Google connection could be attached through a transferable initiation URL — fixed locally

Original evidence: `/api/ios/google-connect` issued a five-minute connection token for the caller's account; `/auth/google` accepted it in a browser URL; `/auth/callback` chose that account and committed Google identity/access/refresh credentials before native callback-code exchange.

Prerequisite and impact: an Apple-only attacker obtained their own linking URL, persuaded a victim to open it within five minutes and complete genuine Google consent, and the victim's Google subject was not already linked to another Week of Us account. The attacker's existing session could then use that connection. Calendar writes additionally required the victim granting write scope. This is a source-confirmed account-linking phishing/CSRF path with user interaction, not a demonstrated live-provider exploit or unauthenticated login bypass.

Commit `cd46eef` stages encrypted credentials on a five-minute completion record and requires the matching authenticated native account plus the separate one-use completion code/state before ownership is committed. State and code must both match. Completion, provider ownership assignment and session creation occur in one transaction; unique identity constraints arbitrate concurrent claims. Invalid initiation tokens now fail closed, and starting a new OAuth flow clears abandoned optional cookies. Apple private-relay email differences remain supported.

Synthetic real-HTTP/PostgreSQL tests passed for missing/wrong/invalid bearer, wrong state, expiry, replay, ordinary sign-in compatibility, concurrent exchange of one code and concurrent claims on one Google subject. Mocked callback tests verify that browser completion alone changes no active identities/connections and stages encrypted token fields only. No Google consent was performed.

Release prerequisite: apply migration 021, then coordinate server and native-client release. Older clients still perform ordinary native sign-in but cannot finalize Calendar linking without the new bearer proof; the server returns an actionable update/retry error. Avoid a mixed deployment that still serves the vulnerable old callback. Migration 021 is additive; keep it during rollback and let short-lived pending codes expire. Reverting the auth code reintroduces the vulnerability and is not a safe remediation rollback. No production migration or release was performed.

### WOU-04 — Medium: native offline drafts could replay into another household — fixed locally

Original evidence: `OfflineStore.swift` keyed queues/caches only by user ID; `PlannerViewModel.swift` flushed pending changes before fetching the current planner, and offline create requests carried no household precondition. The server correctly chose the current session household, so old unassigned creates could be inserted in the new one.

Prerequisite and impact: the same user had an unsynced offline create, changed households on another device/session, then reconnected. Old note/task text could be disclosed to new household members. Existing-item mutations generally failed household predicates; unassigned new creates are the material path. Commit `572e71a` binds caches/queues and every replay to user plus household, checks the fresh server session before replay, and verifies both identity headers in the server authorization boundary. Membership or bearer changes after preflight are rejected without writes. Rejected changes remain durable, and malformed queues cannot be overwritten as empty. Older queues lack a provable household and remain quarantined unchanged; the app surfaces a recovery notice. A manual review/export workflow for those legacy drafts is a remaining product task, not an automatic guess at their destination.

The client clears stale planner data and the stored widget snapshot when it learns the identity changed and requests a widget refresh; WidgetKit controls visible refresh timing. Fully disconnected devices retain previously authorized local cache contents by design. Tests passed for household/account mismatch, scope headers, failed replay retention, old/malformed file preservation and cache identity, plus real HTTP no-write tests after a membership change. The complete native simulator suite passed 112 tests; physical-device behavior was not tested.

### WOU-05 — Medium: private query data in database failure logs — fixed locally

Original `src/lib/server/database.ts:52–54` logged `{ text, values, error }`. Failed statements could include household text, emails, attachment bytes, token hashes or encrypted provider material; PostgreSQL error fields could include entire failing rows. Additional action handlers logged or returned the original error. Log disclosure requires a database failure involving that data and access to retained logs; public log access and decrypted provider credentials were not established. Actual historical log contents were not inspected, so historical exposure is not claimed.

Commit `37979e8` sanitizes database failures at query/transaction boundaries before downstream handlers receive them. Logs/errors retain a generic message and restricted SQLSTATE/network codes, with no original cause, SQL or parameters. Application validation messages remain intact. Five regressions verify query/transaction/pool/connect privacy, successful transactions, rollback and connection disposal on rollback failure. Logs already produced and external database-server logging remain outside this fix.

### WOU-06 — Known production dependency advisories — patched locally; exploitability qualified

The initial lockfile had Next.js 16.3.0 and sharp 0.35.3. Public npm audit reported one critical and one high vulnerable package. Commit `c5053ad` upgrades Next.js/eslint-config-next to 16.3.8 and sharp to 0.35.5 through compatible dependency updates. The post-update production audit reports zero vulnerabilities.

The Windows-hosted RCE advisory does not match the checked-in Linux Docker deployment. The `next/og` advisory requires attacker-controlled image-generation input; no `next/og`/`ImageResponse` use was found. AVIF optimization requires an eligible attacker-controlled image source; no such reachable source was established in this app. These are vulnerable dependency findings, not proof of exploitable production RCE. Primary advisory sources: [Windows hosting](https://github.com/advisories/GHSA-p293-qw3h-jr36), [AVIF optimization](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4), [ImageResponse](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j), [sharp/libheif](https://github.com/advisories/GHSA-rgj7-g3m4-5g8c).

## Smaller backlog and stronger patterns

1. **Conditional medium: viewer-role drift.** Planning/calendar mutations reject viewers, but several household preference/location/hide/restore actions only require household membership. Viewer exists in schema/tests; normal invitations create members and no normal viewer-assignment API was found. Centralize edit-role checks if viewers are supported in real data; no existing viewer population was inspected.
2. **Medium reliability: notification delivery deadlines and session errors.** Google Calendar fetches have an eight-second timeout; APNs HTTP/2 delivery lacks an explicit session error handler/deadline and email/invitation fetches lack an app timeout. Test network failure/hang behavior, add bounded deadlines, and retain durable retry semantics. No live outage was reproduced.
3. **Low privacy: long-lived SSE.** Membership is checked when opening the stream, but not while it remains open. A departed user may receive table-change metadata until disconnect. No row values/titles are streamed. Periodic expiry/membership revalidation would tighten this.
4. **Capacity hardening:** attachments have streaming and decoded 5 MB limits but no aggregate household/user quota visible in code. Verify infrastructure limits before choosing quotas; no capacity attack was attempted.
5. **Development dependencies:** the full npm audit still reports 10 dev-only package findings (8 high, 2 moderate), including glob/YAML processing, Vitest mock-server traversal, and jsdom's undici. Investigate each build/test exposure separately; do not run `audit fix --force`, which proposed downgrading Next's lint configuration across major versions. Production audit is clean.
6. **Invitation consent:** email-matched pending invitations are accepted during login for users without a household. This is documented product behavior, not reported as an auth bypass. Explicit acceptance would make household choice clearer.

Portfolio comparison: the Macros app's `src/client-diagnostics.js` allowlists safe diagnostic fields instead of storing arbitrary payloads; Week of Us's new database error boundary follows that principle. Stuff's session implementation has server-side revocation checks and bounded rotating refresh state; Week of Us already uses opaque, hashed, expiring sessions with fresh membership lookup. Within Week of Us, the existing calendar write path used the acting user's Google token and ETags, while provider search/reminder paths lagged on current owner-membership checks. Existing eight-second Calendar fetch deadlines are a useful pattern for its notification adapters.

## Existing strengths and explicit limits

- 256-bit opaque session tokens, SHA-256 storage, 30-day expiry, HttpOnly/SameSite cookies; database-derived user and household context. Google state/PKCE; Apple issuer/audience/signature/nonce checks. Provider credentials encrypted with AES-256-GCM.
- Parameterized SQL and household predicates dominate persistence. UUID retry identities, transactional recurring-task generation and unique/deduplicated job rows address common replay failures. Calendar writes use actor credentials, write scopes/provider role and ETags.
- New calendars default to Hide. Visibility-aware caches, authenticated attachment reauthorization, octet-stream/attachment/nosniff/no-store downloads, and previews excluding HTML/SVG provide useful privacy/content boundaries. The initially suspected hidden-event Settings leak was ruled out by its visibility filter.
- CSP with per-request nonce, clickjacking restrictions and MIME-sniff protection are configured in application proxy code. Production Docker runs a non-root user. A tracked-text scan found no private-key/AWS/GitHub/Google-key candidates in 288 scanned files; this was not an exhaustive secret/history audit.
- No assertion is made about production patch level/configuration, exploit history, actual private-calendar contents, provider consent roundtrips, Apple/Google grant revocation, email/push delivery, full log retention, disaster restore, signed-device behavior or physical-device acceptance.
